## Exploratory Data Analysis

The EDA investigates:

- Missing values and duplicates

- Machine-level patterns
- Potential target leakage

### Key Findings

- 14,000 missing temperature readings
- 6,703 negative vibration readings
- No duplicate records
- Approximately 80.3% of records belong to Class 0
- Approximately 19.7% of records belong to Class 1
- Systematic negative vibration readings occur at quarter-hour intervals
- Several derived variables present potential target leakage risks

The dataset exhibits class imbalance.

These findings informed the data cleaning, feature selection, preprocessing and evaluation strategies.

## Data Cleaning

Implemented in `src/data_cleaning.py` using the `DataCleaner` class.

Cleaning operations include:

- Dataset loading and validation
- Data type conversion
- Invalid record checking
- Duplicate record checking
- Vibration error handling
- Sensor value validation
- Chronological sorting

### Vibration Correction

A systematic pattern of negative vibration readings was identified at minutes 00, 15, 30 and 45.

Based on the suspected sign-inversion pattern, 6,667 readings were converted to positive values while preserving their magnitude.

This correction is based on an observed data pattern rather than a confirmed hardware fault.

The remaining 36 negative vibration readings were converted to missing values because their validity could not be established.

These missing values are handled during preprocessing.

### Sensor Validation

The cleaning pipeline also checks for:

- Humidity readings outside the valid range of 0 to 100
- Negative pressure readings
- Negative energy consumption readings
- Invalid timestamps
- Missing machine identifiers
- Invalid target labels
- Duplicate records
- Conflicting machine-timestamp records

### Cleaning Results

| Data Quality Issue | Before | After |
|---|---:|---:|
| Total records | 100,000 | 100,000 |
| Duplicate records | 0 | 0 |
| Missing temperature | 14,000 | 14,000 |
| Negative vibration | 6,703 | 0 |
| Missing vibration | 0 | 36 |

No records were removed during the cleaning process.

Missing values are intentionally retained at this stage because imputation must be fitted using the training dataset only.

### Data Cleaning Limitations

- The cause of the systematic negative vibration readings has not been independently confirmed.
- The sign correction assumes that the affected readings have valid magnitudes but incorrect signs.
- Median imputation cannot recover the original missing sensor measurements.
- The effect of vibration correction should be evaluated by comparing model performance with and without the correction.
- The original dataset is retained to support reproducibility and alternative cleaning experiments.

## Feature Engineering

Implemented in `src/preprocessing.py` using the `FeatureEngineer` class.

### Engineered Features

| Feature | Justification |
|---|---|
| hour_sin | Represents cyclical hourly patterns |
| hour_cos | Complements the hourly sine representation |
| day_sin | Represents cyclical day-of-week patterns |
| day_cos | Complements the day-of-week sine representation |
| temperature_missing | Identifies originally unavailable temperature readings |
| vibration_missing | Identifies unavailable or invalid vibration readings |

### Cyclical Time Features

Hours and days of the week are represented using sine and cosine transformations.

This allows the model to represent the cyclical relationship between adjacent periods, such as hour 23 and hour 0.

These features may help identify recurring machine operating patterns.

### Missing-Value Indicators

Missing-value indicators preserve information about unavailable sensor readings before imputation.

This allows the models to distinguish between actual sensor measurements and measurements replaced through imputation.

The predictive usefulness of these engineered features must be assessed during model evaluation and feature importance analysis.

### Potential Data Leakage

The following derived columns are excluded from model inputs as a precaution against potential target leakage:

- machine_status
- anomaly_flag
- predicted_remaining_life
- failure_type
- downtime_risk

These variables may contain information closely related to the maintenance target or information that may not be independently available at prediction time.

Excluding them reduces the risk of obtaining misleadingly high model performance.

The target variable and original timestamp are also excluded from the final model input features.

## Data Preprocessing

Implemented in `src/preprocessing.py` using the `DataPreprocessor` class.

Preprocessing operations include:

- Chronological dataset splitting
- Median imputation
- Standard scaling
- One-hot encoding of machine IDs
- Feature transformation

### Median Imputation

Missing numerical sensor values are replaced using median values calculated from the training dataset.

Median imputation is used because it is less sensitive to extreme values than mean imputation.

A total of 14,036 missing sensor values are handled across the training and testing datasets.

### Standard Scaling

Numerical features are standardised using StandardScaler.

This reduces differences in feature measurement scales and is particularly useful for models such as Logistic Regression.

Tree-based models generally do not require scaling, but the shared preprocessing pipeline provides consistent model inputs.

### Machine ID Encoding

Machine IDs are converted into one-hot encoded features.

Machine identifiers are treated as categorical variables rather than continuous numerical measurements.

This prevents the models from interpreting machine IDs as having an artificial numerical ranking.

The encoder is configured to handle unknown categories without raising an error.

### Prevention of Data Leakage

Imputation, scaling and encoding are fitted using the training dataset only.

The fitted transformations are subsequently applied to the testing dataset.

This prevents testing information from influencing the preprocessing parameters.

### Dataset Splitting

The dataset is divided chronologically using an 80:20 training and testing split.

Chronological splitting is used instead of random splitting to better represent the situation where historical machine readings are used to develop models that are evaluated on later observations.

Records sharing the same timestamp are kept together at the split boundary.

Split timestamp: `2025-02-25 13:20:00`

## Shared Pipeline Usage

All models should use the same dataset splitting and preprocessing approach to ensure fair comparison.

### Method 1: Automated Preprocessing Pipeline

```python
from src.preprocessing import DataPreprocessor

processor = DataPreprocessor()

X_train, X_test, y_train, y_test = processor.run()
```

The returned datasets can be used for model training and final evaluation.

### Method 2: Exported CSV Datasets

```python
import pandas as pd

train = pd.read_csv("data/processed_train.csv")
test = pd.read_csv("data/processed_test.csv")

X_train = train.drop(columns=["maintenance_required"])
y_train = train["maintenance_required"]

X_test = test.drop(columns=["maintenance_required"])
y_test = test["maintenance_required"]
```

The exported CSV datasets provide a convenient alternative for direct model training and final testing.

However, these datasets should not be used directly for cross-validation or hyperparameter tuning because preprocessing has already been fitted on the entire training partition.

### Method 3: Cross-Validation and Hyperparameter Tuning

For cross-validation and hyperparameter tuning, use the raw split and fit preprocessing separately within each training fold.

```python
from src.preprocessing import DataPreprocessor

processor = DataPreprocessor()

X_train, X_test, y_train, y_test = processor.prepare_raw_data()

preprocessor = processor.build_preprocessor()
```

The preprocessor can then be included in a scikit-learn Pipeline.

```python
from sklearn.pipeline import Pipeline
from sklearn.linear_model import LogisticRegression

pipeline = Pipeline([
    ("preprocessor", preprocessor),
    ("model", LogisticRegression(max_iter=1000))
])
```

Time-aware validation should be used, keeping identical timestamps together within validation boundaries.

The final testing dataset must not be used for hyperparameter tuning or model selection decisions during training.

## Model Evaluation

Implemented in `src/evaluation.py` using the `ModelEvaluator` class.

### Evaluation Metrics

| Metric | Purpose |
|---|---|
| Accuracy | Measures overall prediction correctness |
| Precision | Measures the proportion of maintenance predictions that are correct |
| Recall | Measures the proportion of actual maintenance cases successfully detected |
| F1-score | Balances precision and recall |
| ROC-AUC | Measures the ability to distinguish between target classes across thresholds |
| Average Precision | Summarises precision-recall performance |
| Confusion Matrix | Identifies correct predictions, false alarms and missed maintenance cases |
| Classification Report | Provides class-specific performance metrics |

### Evaluation Metrics Justification

Accuracy alone is insufficient because approximately 80% of the dataset belongs to the majority class.

Recall is particularly important because failing to identify a machine requiring maintenance may result in unexpected downtime or equipment damage.

Precision is also important because unnecessary maintenance alerts may increase operational costs.

F1-score provides a balance between precision and recall.

Average Precision is useful for assessing positive-class detection in an imbalanced dataset.

ROC-AUC provides an additional measure of the model's ability to distinguish between maintenance and non-maintenance cases.

Final model selection should consider multiple metrics rather than accuracy alone.

### Evaluation Usage

After training a model:

```python
from src.evaluation import ModelEvaluator

y_pred = model.predict(X_test)
y_prob = model.predict_proba(X_test)[:, 1]

evaluator = ModelEvaluator("Model Name")

results = evaluator.run(y_test, y_pred, y_prob)
```

The probability input represents the probability of Class 1.

### Evaluation Visualisations

```python
import matplotlib.pyplot as plt

plt.show()

evaluator.plot_roc_curve(y_test, y_prob)
```
